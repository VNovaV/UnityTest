## 三、技术勘误

原清单有几处内容在 2024 年之后已经过时或不严谨。这些点我在新清单里做了修正，单独列出来说明原因。

| 原条目 | 问题 | 建议做法 |
|---|---|---|
| WASD 基础输入处理（GetAxisRaw） | 旧 Input Manager，已不是官方推荐做法 | 学 **New Input System**：Input Actions 资产 + 设备无关绑定 + 输入层封装。见 S-03 |
| 长按加速跑（Lerp 平滑切换速度） | Lerp 的 t 参数**不是帧率无关的**。直接写 Lerp(a, b, t) 在 144fps 下会比 60fps 下明显更快 | 用 1 - exp(-k * dt)，或用 MoveTowards / SmoothDamp。见 L1-16 |
| 血条平滑过渡（Slider.value + Lerp） | 同上 | 同上。也可以直接用 DOTween，但要明白它在背后做了什么 |
| 四元数平滑旋转（Quaternion.Slerp） | 同样存在 t 的帧率问题；Slerp 有轻微超调风险 | Quaternion.RotateTowards，或带 1 - exp(-k * dt) 的 Slerp |
| 读取玩家设置（PlayerPrefs.HasKey 判断） | 多余。GetXxx(key, defaultValue) 本身就带默认值 | 直接 GetInt / GetFloat(key, default)，少一次调用和一次分支 |
| 二进制存档（BinaryFormatter / 自定义序列化） | **BinaryFormatter 已被标记过时且存在反序列化安全漏洞**，.NET 5+ 与新版 Unity 不推荐使用 | 手写二进制读写（BinaryReader/Writer），或 MessagePack，或干脆继续用 JSON |
| 对象池复用子弹（自定义 Pool 类） | Unity 2021+ 已内置 UnityEngine.Pool.ObjectPool 与 LinkedPool | **先自己写一版**理解原理，再看官方实现做对比（这也是 L2-01 的验收方式）|
| 距离衰减计算（1 / (1 + distance * factor)） | 物理上正确的衰减是 1/d²，但这个公式不是 | 知道两者差别：真实衰减太陡、听感差；游戏里通常用可调曲线。结论上原清单的选择是对的，但要知道为什么 |
| 异步任务链（async / await + UniTask） | 没提取消和异常处理，而这两点才是异步的真正难点 | 补上 CancellationToken、异常捕获、生命周期绑定。见 L2-24 |
| 协程 vs Update 性能对比 | 微优化，收益极小却容易被当成重点 | 降参考区。先把架构做对，再谈这种级别的优化 |
| 列表遍历优化（for vs foreach vs LINQ） | 同上，除极端热路径外收益可忽略 | 降参考区。只需记住一条：别在每帧的 Update 里写 LINQ |
| 云存档同步（基础框架预留） | 在单机小项目里是纯负担 | 删 |
| 行为树基础框架 | 对中小体量项目是过度设计 | 参考区。状态机够用，等真的需要再学 |

## 四、参考区怎么用

剩下的约 125 条不是「不用学」，而是**「不需要现在专门练」**。用法：

### 允许进入参考区的三个触发条件

1. **项目里真的遇到了。** 做项目时卡在某个具体问题上，回参考区找到对应条目，现学现用。这是收益最高的方式。
2. **面试被问到。** 求职向的话，面试前一周扫一遍参考区，把「知道它存在」升级成「能说两句话」。
3. **想做一个具体功能，而它恰好在这里。** 例如你突然想做小地图，就去查「小地图（Camera + Render Texture）」。

### 一条禁令

**不许为了「把参考区刷完」而去碰参考区。**

这会把 194 条的清单变回原样——你又会回到「每样都碰过，每样都不会」的状态。
参考区存在的意义就是让你**心安理得地不学它**：你知道它在那儿，需要的时候找得到，这就够了。

## 五、原清单的保留价值

原清单不用删，把它当**查询表**用：

- 想不起某个功能该用什么 API 时，扫一眼关键词（它的关键词标注做得很好）
- 做项目时想给项目加点什么，从里面挑灵感
- 每完成一个阶段，扫一遍，看有没有「原来还有这个东西」的遗漏感——**只扫，不动手**

它是一本好字典。字典的用法是查，不是背。
