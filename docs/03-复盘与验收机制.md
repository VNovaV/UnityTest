# 03 · 复盘与验收机制

> 这份计划里最容易被跳过、但决定成败的就是这个文件。
> 没有验收和复盘，项目做完就忘了，做十个和做一个没区别。

---

## 一、验收四问

每条清单、每个模块做完，用这四问自检。**任何一问答不上来，就标回去重做。**

1. **能重写吗？**
   关掉代码和教程，从空文件把核心模块再写一遍。写不出来 = 没学会。

2. **能解释吗？**
   用自己的话说明「为什么这么写」，以及「另一种写法的代价是什么」。
   （例：为什么不直接改 transform.position？为什么事件比直接引用好，什么时候又不好？）

3. **能定位吗？**
   故意把某处改坏，看自己能不能在 15 分钟内定位到问题出在哪一层。
   这是「会用」和「会调」的分界线。

4. **能讲吗？（求职版新增，最重要的一问）**
   假设面试官坐你对面，让你针对这个模块讲 3 分钟。你能讲出「为什么这么做」、「另一个方案的代价是什么」、「有什么具体数字」吗？
   答不上来，说明你只是「做出来了」，还没有「拥有它」。
   **求职期：这一问的优先级高于前三问。**

## 二、白板重写 SOP

每个阶段结束时做一次，每次挑 1-3 个模块，全程 60-90 分钟。

**准备**
1. 新建一个空 Unity 项目（或空文件夹）
2. 关掉原项目、关掉教程、关掉浏览器
3. 只允许查官方 API 文档，**不允许看自己的旧代码**

**执行**
4. 写下来，允许卡住，允许写得丑
5. 卡住超过 20 分钟才能看一眼旧代码，看一眼后立刻关掉继续写

**收尾**
6. 对比新旧两版，把差异记进复盘：「哪里忘了、哪里写得更差、哪里其实进步了」
7. 记不住的 API 名字单独列一个清单，用间隔重复（Anki 之类）记，**只记「它存在、用来干嘛」，不背签名**

> 注意：白板重写不是为了「复现」你的代码，而是为了检验**大脑里有没有可重建的模型**。
> 写得不一样完全没关系。

## 三、复盘模板

每个项目 / 每个阶段结束时，在项目目录下建一个 复盘.md，照着填。
**不许写「收获很多」这种话，只写具体的事。**

### 项目复盘 · （项目名 / 日期）

**1. 做完了什么**
- 实际交付了什么（构建包、截图、视频）
- 实际花了多少小时，和预估差多少，为什么差

**2. 卡最久的三件事**
- 问题是什么（具体到现象，例如「子弹穿过薄墙」）
- 卡了多久
- 最后怎么解决的
- **下次遇到同类问题，我会先检查什么**

**3. 我改了主意的设计**
- 原本打算怎么做，后来为什么改
- 这个改动让哪部分变好了，哪部分变差了

**4. 白板重写结果**
- 哪些模块一次写出来，哪些忘了
- 忘掉的部分是什么原因（没理解 vs 没记住）

**5. 三个具体的技术收获**
- 必须是能说给别人听的句子，不是名词堆砌
- 反例：「学会了对象池」
- 正例：「池对象复用时最容易漏的是重置物理速度，我因为漏了它出现过子弹刚出池就乱飞的 bug」

**6. 还没解决的坑**
- 明确记下来，避免下次重蹈

**7. 下一个项目要改的一件事**
- 只写一件，写多了就等于没写

## 四、周节奏（以每周 12 小时为例）

| 时段 | 时长 | 做什么 |
|---|---|---|
| 平日晚上 × 3 | 各 1.5-2h | **做项目**（主线，必须占大头） |
| 周末一天 | 4h | **学新条目 + 立刻塞进项目里用一次** |
| 周末另一天 | 2h | **复盘 + 整理笔记 + 补提交 + 规划下周** |

三条硬规则：

1. **项目时间不许被学习时间挤占。** 反过来的情况很常见：每天都在看教程，项目永远停在 M1。这是「教程地狱」。
2. **新学的东西必须在 48 小时内用进项目。** 否则一周后忘光。
3. **每周必须有可见产出。** 周日晚上问自己：这周我手上多了什么能跑的东西？

## 五、卡住的两小时规则

**规则：任何问题，先自己扛 2 小时。**

以 2 小时为界，按顺序求助：

| 顺序 | 做什么 | 说明 |
|---|---|---|
| 1 | 重读报错 | 90% 的答案是报错里写着的，真的 |
| 2 | 加日志 / 断点，缩小范围 | 把「不行」拆成「哪一步开始不行」 |
| 3 | 查官方文档 | 优先官方，其次论坛 |
| 4 | 搜索报错原文 | 搜英文报错，命中率高一倍 |
| 5 | 问人 / 发帖 | 提问时带上：想做什么、试了什么、报错是什么、最小复现 |

**两个例外，可以立刻查：**
- 纯粹记不住的 API 名字（直接查，不值得卡）
- 环境 / 配置问题（装不上、编译不过、路径不对这类，不是能力问题）

**一个反例外：**
手感调参、数值平衡、UI 手感这类**主观**问题，永远不要查别人的数值。
抄来的数值一定不适合你的游戏，而且会掩盖你没想清楚这件事。

## 六、反模式清单

对照检查，中了任何一条就立刻停手纠正。

| 反模式 | 表现 | 后果 | 解法 |
|---|---|---|---|
| 教程地狱 | 每天都在看教程，项目停在 M1 | 永远在学，永远做不出东西 | 项目时间不许被挤占；新知识 48 小时内必须用一次 |
| 广度错觉 | 「194 条我都见过」 | 每样都会一点，每样都做不深 | 只有 44 条必修；其余承认自己「知道它存在」就够了 |
| 收藏代替学习 | 存了几十个 G 的教程和资产包 | 心理上以为已经拥有 | 收藏夹只留正在做的项目相关的 |
| 完美主义重构 | 系统还没跑通就开始抽接口 | 项目永远完成不了 | 先能跑，再优化，最后抽象 |
| 范围膨胀 | 中途想加新功能 | 项目烂尾 | 范围只许减不许加，加一个必须先删一个 |
| 只看不写 | 视频看完点个赞就过去了 | 虚假的掌握感 | 每个视频看完必须立刻写 20 行代码 |
| 不提交 | 三周才 commit 一次 | 不敢改，怕回不去，于是学不会架构 | 每天至少一提交 |
| 不玩自己的游戏 | 只测功能，不完整玩一遍 | 自己都不知道游戏哪里难受 | 每周完整通关一次自己的游戏 |
| 跳过复盘 | 「没什么好总结的」 | 做完就忘，做十个等于做一个 | 复盘是硬性交付物，和构建包同等级 |

## 七、阶段结束的自检清单

每完成一个阶段（L1 / L2 / 一个项目），跑一遍：

- [ ] 出口标准全部达成（见 01、02 号文件）
- [ ] 白板重写做过，且记下了忘掉的部分
- [ ] 复盘文档写完，7 个部分都填了
- [ ] 项目已提交，构建包能跑
- [ ] 完整玩过一遍自己的项目，记下了 3 个最难受的点
- [ ] 更新了 README 里的进度看板
- [ ] 决定了下一阶段砍掉什么（是的，要主动砍，不要贪）

## 八、求职版附加机制（校招）

### 8.1 每个功能做完的「谈资自检」

- 这个功能解决了什么问题？没有它会怎样？
- 我为什么选这个方案？另一个方案的代价是什么？
- 有什么数字能证明它有效？
- 面试官会往哪里追问？我能答到第几层？

**答不满三条的功能，要么补技术含量，要么从简历里删掉。**

### 8.2 每周一次「讲给自己听」

- 录 5 分钟，讲你这周做的模块
- 回看时只找三个毛病：有没有跳过过程、有没有数字、有没有体现你的判断
- 坚持到 W21，你会发现自己讲得比大多数人清楚

### 8.3 八股复盘法：背链条，不背结论

不要记「Unity 的 GC 会卡帧」这种结论，要记完整链条：

**现象 → 原因 → 影响 → 对策 → 代价**

例（GC）：每帧 new 产生托管堆分配 → 堆增长触发 GC → GC 暂停主线程 → 表现为周期性卡顿 → 对策是对象池 + 避免装箱 + StringBuilder → 代价是代码复杂度上升、常驻内存变高。

能走完这条链才算真的会。只记结论的话，面试官一句「那 Unity 的 GC 为什么不用分代」就露馅了。
